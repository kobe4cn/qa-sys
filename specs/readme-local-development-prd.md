# README 本地开发指南 PRD

## Problem Statement

`qa-sys` 是一个用于练习 Rust、HTTP、gRPC、PostgreSQL、Redis 和 Pulsar 的示例项目，
但目前缺少可供本地使用者直接执行的根级使用说明。学习者无法从项目入口文档中判断项目
包含哪些组件、应先启动哪些依赖、如何初始化数据库、如何分别启动 `qa-svc` 与 Gateway，
也无法通过一条完整业务链路确认环境是否真正可用。

使用者主要通过 Apple `container` 管理本地容器，同时也需要 Podman 作为可选方案。
如果没有统一、可发现的自动化入口，两种容器引擎的命令容易发生漂移，数据卷的保留与删除
语义也不清晰，可能造成启动失败或误删练习数据。此外，项目当前包含仅适合教学场景的安全
实现，如果 README 不明确提示，使用者可能错误地将示例配置理解为生产实践。

## Solution

提供一份面向本地学习者的中文 README，并将本地依赖管理集中到 Makefile 的公开目标中。
README 从项目定位、架构和前置条件开始，分别给出 Apple `container` 与 Podman 的从零启动
流程，再指导使用者在两个前台终端中启动 `qa-svc` 和 Gateway。

依赖启动流程使用固定版本的 PostgreSQL、Redis 和 Pulsar 镜像，默认通过项目专用命名卷
持久化数据。普通停止操作只删除容器并保留数据；只有名称明确的 reset 操作才删除项目专用
数据卷。数据库迁移会识别“未迁移”“已完整迁移”和“部分迁移”三种状态，避免重复执行或
覆盖异常数据库。

README 提供一条可复制的 HTTP 验证流程，通过注册、登录、Bearer Token、创建问题和查询问题
列表验证从 Gateway 到 `qa-svc`，再到 PostgreSQL、Redis 和 Pulsar 的完整链路。文档同时列出
端口、配置入口、测试命令、常见问题以及非生产安全限制。

## User Stories

1. 作为首次接触项目的学习者，我希望立即理解 `qa-sys` 的练习用途，以便判断它是否适合我的学习目标。
2. 作为本地使用者，我希望看到醒目的非生产环境声明，以便不会误用示例实现。
3. 作为 Rust 学习者，我希望了解 workspace 中各模块的职责，以便快速找到需要阅读的代码。
4. 作为系统学习者，我希望看到 HTTP、gRPC 和各基础设施组件之间的数据流，以便建立整体架构认知。
5. 作为 Apple Silicon Mac 使用者，我希望知道 Apple `container` 的系统要求，以便在启动前确认环境兼容。
6. 作为 Apple `container` 使用者，我希望通过一条 Make 命令启动全部依赖，以便避免手工维护多个容器命令。
7. 作为 Podman 使用者，我希望获得与 Apple `container` 对等的启动入口，以便使用自己熟悉的容器引擎。
8. 作为尚未安装容器工具的学习者，我希望文档链接到官方安装说明，以便获得可信且最新的安装步骤。
9. 作为本地使用者，我希望依赖镜像版本固定，以便不同时间启动时获得可重复的练习环境。
10. 作为本地使用者，我希望 PostgreSQL、Redis 和 Pulsar 使用项目专用名称，以便与其他本地项目区分。
11. 作为学习者，我希望普通停止操作保留数据库和消息数据，以便下次启动后继续练习。
12. 作为需要重新开始的学习者，我希望有明确的数据重置命令，以便恢复干净环境。
13. 作为谨慎的使用者，我希望 reset 操作明确提示会删除数据，以便避免误删练习成果。
14. 作为同时运行多个环境的开发者，我希望能够覆盖容器名前缀和端口，以便隔离验证环境。
15. 作为本地使用者，我希望能够检查每个依赖是否就绪，以便区分“容器已启动”和“服务可接受请求”。
16. 作为本地使用者，我希望就绪检查具有明确超时，以便依赖异常时不会无限等待。
17. 作为首次启动者，我希望通过 Make 命令执行数据库迁移，以便不必了解容器内的 `psql` 用法。
18. 作为重复启动项目的学习者，我希望迁移命令可以安全地重复执行，以便不因表已存在而失败。
19. 作为遇到异常数据库状态的使用者，我希望部分迁移状态被拒绝并解释原因，以便不会继续破坏数据。
20. 作为本地使用者，我希望知道应先启动 `qa-svc` 再启动 Gateway，以便避免 gRPC 连接失败。
21. 作为学习者，我希望两个应用进程保持前台运行，以便直接观察日志并练习排障。
22. 作为本地使用者，我希望应用启动命令自动选择正确配置，以便无需手工设置容易出错的环境变量。
23. 作为 API 学习者，我希望通过注册请求验证 Gateway 能接收并校验 JSON，以便确认 HTTP 入口正常。
24. 作为 API 学习者，我希望通过登录获得 Token，以便理解示例项目的会话流程。
25. 作为 API 学习者，我希望携带 Bearer Token 创建问题，以便验证受保护路由。
26. 作为 API 学习者，我希望携带 Bearer Token 查询问题列表，以便验证持久化结果和鉴权中间件。
27. 作为重复执行示例的使用者，我希望知道用户名重复注册会失败，以便选择新用户名或重置数据。
28. 作为接口探索者，我希望 README 指向 HTTP 路由和 gRPC 合约的权威定义，以便进一步了解完整接口。
29. 作为本地使用者，我希望看到所有服务端口及其用途，以便排查端口占用和连接问题。
30. 作为贡献者，我希望看到分层测试目标，以便选择单元、集成或端到端验证。
31. 作为 Apple `container` 使用者，我希望 Pulsar 获得足够内存，以便避免因默认虚拟机资源不足而启动失败。
32. 作为 Podman 使用者，我希望 Podman machine 未启动时获得清晰提示，以便知道需要先修复运行环境。
33. 作为维护者，我希望两种容器引擎共用镜像、端口和命名变量，以便减少自动化配置漂移。
34. 作为维护者，我希望 README 中的命令全部映射到公开 Make 目标，以便让自动化入口保持可发现。
35. 作为维护者，我希望所有删除操作只作用于精确的项目资源名，以便避免影响其他本地容器和数据卷。
36. 作为安全意识较强的学习者，我希望了解密码哈希、加密 IV、示例密钥和本地密码的限制，以便不把它们当作生产实践。

## Implementation Decisions

- 根 README 使用中文说明，命令、配置键、模块名和协议标识符保留原始英文。
- README 的主要受众是从零开始在本地运行项目的学习者，而不是生产部署人员。
- 本地自动化继续使用现有 Makefile，不引入 Docker Compose、Podman Compose 或额外 shell 脚本。
- Apple `container` 是主要快速开始路径，Podman 是紧邻其后的等价替代路径。
- 两种容器引擎提供明确分离的公开目标，不通过隐藏状态自动推断当前容器引擎。
- 公开生命周期接口包括依赖启动、就绪检查、数据库迁移、停止和数据重置；两种引擎使用对应后缀。
- 应用公开接口包括前台启动 `qa-svc` 和前台启动 Gateway，两个进程不在 Makefile 中后台化，也不维护 PID。
- PostgreSQL、Redis 和 Pulsar 使用固定版本镜像；两种引擎共享镜像、端口、容器名和卷名变量。
- 容器和卷使用可覆盖的项目名前缀，端口也允许覆盖，以支持并行或隔离验证。
- PostgreSQL 初始化本地 `qa_sys` 数据库；本地账号、密码和服务地址与现有应用配置保持一致。
- PostgreSQL 和 Redis 各使用一个命名卷；Pulsar 的数据与日志分别使用命名卷。
- Apple `container` 启动 Pulsar 时显式配置 2 GiB 内存。
- 依赖启动会重建精确命名的项目容器，但不会删除命名卷。
- 普通停止操作删除精确命名的项目容器并保留全部命名卷。
- 数据重置操作删除精确命名的项目容器和命名卷，并在执行时明确说明数据将被清空。
- 不使用全局删除、全局 prune 或其他可能影响非项目资源的命令。
- 就绪检查覆盖 PostgreSQL、Redis 和 Pulsar，并为每个依赖设置最多 60 次、每次间隔一秒的有界重试。
- 数据库迁移通过四张核心业务表判断状态：全部不存在时迁移，全部存在时成功跳过，部分存在或输出异常时失败。
- 迁移启用 SQL 遇错即停，防止错误后继续执行。
- `qa-svc` 使用根应用配置启动；Gateway 使用其专属配置目录启动。
- README 明确要求先启动 `qa-svc`，再启动 Gateway。
- README 的最小业务验收链路为注册、登录、创建问题和查询最新问题。
- 创建问题和查询最新问题均携带登录得到的 Bearer Token，因为两者都是受保护路由。
- README 列出 HTTP、gRPC、指标、PostgreSQL、Redis、Pulsar 协议端口和 Pulsar 管理端口。
- README 将 HTTP 路由实现和 gRPC 协议定义标记为完整接口的权威来源。
- README 解释重复注册失败是持久化数据下的预期行为，并给出更换用户名或显式重置两种处理方式。
- README 明确记录密码哈希、固定 IV、仓库内示例密钥、本地服务密码、密钥轮换、限流和生产部署方面的限制。
- 本次需求不改变数据库模式、HTTP API 合约、gRPC API 合约或 Rust 业务逻辑。

## Testing Decisions

- 采用一个最高层测试接缝：从 README 公开的 Makefile 接口进入，完成依赖启动、迁移、应用启动和 HTTP 业务闭环。
- 好的测试只观察使用者可见行为，包括命令退出状态、依赖就绪状态、迁移结果、HTTP 状态和响应数据，不断言 Makefile 内部命令排列或 Rust 私有实现。
- Apple `container` 使用独立的测试前缀和非默认端口执行实际端到端验证，避免接触使用者现有容器和数据卷。
- 首次迁移应成功创建四张核心业务表；第二次迁移应识别完整状态并成功跳过。
- HTTP 验证应确认注册成功、登录返回非空 Token、携带 Token 可创建问题，并能在最新问题结果中观察到创建的数据。
- 未携带 Token 的受保护请求不属于 README 主流程，但现有 Gateway 集成测试继续作为鉴权行为的先例和回归保护。
- Podman machine 可用时使用相同的隔离参数执行同一端到端接缝；不可用时只验证公开目标的命令展开，并明确记录未执行运行时验证的原因。
- Makefile 静态验证应确认所有公开目标可展开、迁移启用遇错即停、删除命令只包含项目派生的精确资源名。
- README 静态验证应确认必需章节、公开目标、配置引用、端口、Bearer Token 和安全限制均存在。
- README 本地链接必须解析到仓库内的有效目标，Markdown 代码块必须闭合。
- 既有 Gateway HTTP 集成测试和端到端问答流程测试是本规格的测试先例；它们已覆盖注册、登录、受保护路由和问题创建等外部行为。
- 既有 `qa-svc` gRPC 集成测试是服务层行为先例；它覆盖注册、登录、Token 校验及核心问答操作。
- 本次只修改文档与自动化时，不机械运行无关的 Rust 全量门禁；如果实现过程中改变 Rust 源码、公开 API 或清单，则必须执行项目规定的完整 Rust 门禁。
- 验证结束后只删除具有独立测试前缀的容器和卷，不删除默认开发环境资源。

## Out of Scope

- Kubernetes、Helm、云环境和生产部署说明。
- Docker Compose、Podman Compose 或其他编排文件。
- 将 `qa-svc` 或 Gateway 容器化。
- 在 Makefile 中后台运行应用、管理 PID 或提供守护进程能力。
- 自动创建、启动或修改全局 Podman machine。
- 完整列举所有 HTTP 和 gRPC 接口。
- 修改数据库模式、业务接口或现有迁移内容。
- 修复现有密码哈希、AES-CBC 固定 IV、密钥管理、限流或其他生产安全问题。
- 提供生产级身份认证、授权、TLS、Secret Manager、监控或高可用方案。
- 为 Windows、Linux Docker Engine 或非 Apple Silicon macOS 提供专门流程。

## Further Notes

- 当前根 README 为空，因此本规格定义的是完整的首次使用体验，而不是对既有文档的小幅修订。
- Apple `container` 需要 Apple Silicon 和受支持的 macOS；README 应链接其官方安装与使用资料。
- Podman 安装和 machine 管理应引用官方资料，项目自动化只检查当前运行环境，不替使用者改变全局状态。
- 命名卷默认持久化是有意设计；数据清理必须由使用者显式选择 reset 目标。
- 示例配置中的凭据只用于本地学习环境，不能作为生产凭据示例。
- 实施时应保留工作区中与本规格无关的既有修改，并将本规格相关变更独立提交。
